# Project Coding Rules — Gymie

> Feature Context Docs: See `docs/features/subscription-quantity-chaining.md` for the subscription-quantity/chaining design.

## Development Focus & Data

1. **Only build the current app.** Write tests and code for how the app works now and for the new ideas we're building — never to accommodate legacy behavior, stale demo records, or hypothetical data from earlier iterations. Do not add fallbacks, branches, or compatibility layers that exist only to keep old data shapes working.
2. **Dev data is disposable.** The local database accumulates fake/test data. Agents are authorized to wipe it whenever old or faulty data gets in the way of developing or verifying the current app — reset the members and related records without asking.
3. **Clean dev reset:** `php artisan migrate:fresh`, then `php artisan db:seed --class=ShieldSeeder`, then `php artisan db:seed --class=UserSeeder` gives a clean slate with just the owner account. Owner credentials come from the `OWNER_NAME` / `OWNER_EMAIL` / `OWNER_PASSWORD` vars in `.env` (default `test@example.com` / `test`) and are bootstrap-only — the `UserSeeder` creates the owner if absent and never modifies an existing account, so the env values are never re-applied to a running install. Do NOT run the full `DatabaseSeeder` — it recreates demo members/subscriptions/invoices that are exactly the faulty test data we're trying to avoid.
4. **Real validation uses real flows, not hand-crafted seed states.** Do not validate check-in or membership states by hand-inserting `subscriptions`/`invoices`/`plan_check_ins` rows that force a state (e.g. a fake `TestOverrideMembersSeeder` member with an artificially unpaid invoice + exhausted uses). Instead, create a normal member, attach a real subscription, and let invoices/check-ins generate with real future due dates and real `limit_uses` counts so the production logic (`serviceStatesForMember`, `effectiveStatus`, `remainingUses`) surfaces `unpaid`, `overdue`, `uses_exhausted`, `same_day_duplicate` naturally. Hand-crafted seed members bypass business rules and hide regressions — they may be used for quick manual UI spot-checks, but never as proof that a reorder or severity change is correct.

## Version Control & Commits

1. **Commit after every completed task, not just at the end of a session.** Once what was asked for is done and working, commit before starting the next task. Each commit is a recovery checkpoint — if a later change breaks something, or a session ends unexpectedly, we lose work only back to the last commit, not the whole session.
2. **Don't leave work only on disk because it's incomplete.** If a task has to stop partway (blocked, session cut off, out of context), commit what exists with a `WIP:` prefix rather than leaving it uncommitted. An uncommitted change is what gets lost — a rough WIP commit is always recoverable.
3. **WIP is a floor, not a target.** When a task is actually finished, its final commit should represent a working state (relevant tests passing) — `WIP:` is for genuine mid-task checkpoints, not a way to commit broken code as done.
4. **Write descriptive commit messages** — what changed and why. Git already timestamps every commit automatically, so there's no need to hand-add a date/time; a clear message plus `git log` gives us the "when" for free.
5. **Keep each commit scoped to one logical change.** Don't fold an unrelated fix into the same commit as a feature — it makes it harder to revert or bisect just the part that later turns out to be the problem.
6. **Never treat public-clean as your development branch. dev is the source of truth.** `public-clean` is a filtered, sanitized view of `dev` for publishing to GitHub (`JeremyBarrera/gymie` `main`); all development, commits, and merges happen on `dev`. Do not commit, merge, or `git checkout public-clean` to make changes — `public-clean` is only updated via `scripts/sync-public-branch.ps1` from `dev`.

## How to Publish When Done

1. **Work only on `dev`.**
2. **From `dev` run `scripts/sync-public-branch.ps1` — regenerates `public-clean`.**
3. **`git push origin public-clean:main --force` — updates public GitHub. Never `git checkout public-clean` to edit or `git push origin dev`.**

## Production Readiness, Robustness & Scalability

1. **Validate all user input server-side — never trust the client.** Every form (Livewire component, Filament resource, public scan/signup endpoint) must validate through Laravel validation rules or Form Requests, even for fields the UI already constrains (dropdowns, split phone inputs). Client-side constraints are a UX nicety, not a security boundary.
2. **Wrap multi-step writes in a database transaction.** Any action touching more than one table (or the same table twice) as a single unit of work — creating a member plus its subscription and invoice, approving a signup, recording a check-in — must run inside `DB::transaction()` so a failure partway through can't leave half-written data behind.
3. **Back app-level checks with DB-level guarantees wherever two requests could race.** Validation in PHP (like the duplicate-member check) can still pass twice under concurrent requests; where that matters, add a unique index or `lockForUpdate()` inside the transaction rather than relying on the app-level check alone.
4. **Eager-load relationships on every table/list view.** N+1 queries are the most common source of slowdown as member and location counts grow — use `with()`/`load()` for anything a column, badge, or count depends on, and check new views for N+1 before considering them done.
5. **Authorization is enforced server-side, not just hidden in the UI.** Hiding a button for a role isn't the same as blocking the action — every action that mutates data must check the relevant Shield policy/permission in the backend, so a crafted request can't bypass what the UI merely hides.
6. **Rate-limit public, unauthenticated endpoints.** The scan/signup/check-in routes are reachable by anyone with the QR code — apply Laravel's `throttle` middleware (or a custom limiter) so they can't be abused for spam signups or brute-forcing phone/ID lookups without requiring a login.
7. **Push anything not needed for the immediate response onto a queued job.** Notifications, broadcasts, emails, and similar side effects shouldn't run synchronously — queue them so check-in and signup flows stay fast, and stay resilient if a downstream service is slow or down.
8. **Migrations must be reversible and safe against real data.** Implement `down()` for every migration, and don't assume the table is empty — a migration that's fine against dev's disposable data but corrupts a real gym's data in production isn't production-ready.
9. **No secrets or environment-specific values in code.** API keys, webhook URLs, and per-deployment config belong in `.env`/config files, never hardcoded — same principle as the "no hardcoded colors" styling rule below, applied to anything that changes per environment.
10. **Handle and log the failure case, not just the happy path.** Any external call (notifications, broadcasts, future integrations) can fail — catch it, log it with enough context to debug later, and fail visibly to the user/staff rather than silently swallowing the error.
11. **Index the columns real queries filter or sort on.** As locations and members scale up, audit new queries against `location_id`, `contact`, `government_id`, and status columns for a supporting index — these are exactly what the duplicate check, check-in scan, and location-scoped views filter on.

## Member Duplicate Rule

1. **A new member is blocked only when name + government ID + contact (phone) all match an existing member.** Email is NOT part of the duplicate check. If any one of those three differs, the signup is allowed — identifiers (phone numbers, government IDs) may repeat across members as long as the name differs.
2. **The duplicate check runs at both submission and confirmation.** The public scan endpoint checks on submit; `MemberApplicationService::validateSignup()` and `duplicateExists()` re-check inside the approval transaction to guard against concurrent signups.
3. **Implementation:** `Member::findDuplicateByIdentifiers()` in `app/Models/Member.php`. Callers: `CheckInScanController`, `MemberApplicationService`, `CheckInController`.

## Translations (i18n)

1. **Never hardcode user-facing strings** in Blade templates, Filament forms, tables, or PHP classes. Always use `__('app.key.subkey')` or `App::getLocale()` helpers.
2. **All translation keys must exist in all 5 locale files** under `resources/lang/{ar,en,es,fa,fr}/app.php`. When adding a new key, add it to every locale in the same commit.
3. **No raw lang key strings as placeholders or labels.** If a placeholder like `__('app.placeholders.select_foo')` is referenced, the key MUST exist in the lang files. A missing key returns the raw path string (e.g. `app.placeholders.select_foo`) which is not understandable by users.
4. **Existing locale keys to keep in sync:** When the English file adds a new key under `placeholders`, `fields`, `navigation`, `reception`, `ui`, etc., mirror it into ar/es/fa/fr before merging.
5. **Run `php artisan test` after lang changes** to confirm no broken references.

## Styling (Filament + Tailwind)

1. **Use Filament components** (`<x-filament::section>`, `<x-filament::button>`, `<x-filament::icon>`, `<x-filament::badge>`, `<x-filament-panels::page>`) for all styled UI elements in admin panel views.
2. **Use Tailwind utility classes for layout only** (`flex`, `grid`, `gap-*`, `space-y-*`, `p-*`, `m-*`). Do not use raw color utilities (`bg-gray-50`, `text-gray-950`, `dark:bg-gray-800/50`).
3. **Use Filament CSS classes** (`fi-text`, `fi-text-muted`, `fi-section`, etc.) for text and element styling when available. These respect Filament's theme and dark mode automatically.
4. **Public-facing pages** (under `resources/views/checkin/`) use CSS custom properties (`var(--c-*)`) from the theme-colors partial for location-specific theming. Do not add raw Tailwind color utilities to these views.
5. **No custom CSS in `<style>` blocks** unless absolutely necessary (e.g., animations, print styles). Prefer Tailwind utilities and Filament components.
6. **Admin sidebar width is fixed — do not change it.** The panel's `->sidebarWidth('15rem')` in `app/Providers/Filament/AdminPanelProvider.php` is set so nav labels don't get cut off in Arabic/Persian (and other locales). Never narrow it or switch to a collapsed-by-default sidebar; the collapse button (from `->sidebarCollapsibleOnDesktop()`) must remain user-triggered only.
7. **No hardcoded backgrounds in non-public views.** In admin panel views, Filament pages, and their custom CSS, never use raw color values (`#fff`, `#f9fafb`, `rgba(...)`) for backgrounds. Always use the app's theme variables (`var(--primary-*)`, `var(--gray-*)`, `var(--danger-*)`, etc.) so backgrounds follow the configured theme and dark mode automatically. (Public-facing checkin views are the exception — they use `var(--c-*)` from the theme-colors partial, per rule 4.)
8. **Standalone public-facing views must put their background on `html`, not just `body`.** `body { min-height: 100vh }` only covers the initial viewport — when the page content is taller (e.g. a long signup form), scrolling past 100vh reveals the default white background underneath. Putting the gradient on `html` covers the full scroll area. Also always include `min-height: 100dvh` as a fallback for mobile browser chrome.
9. **Hide native spin buttons on numeric inputs.** All `TextInput::make()->numeric()` fields in admin panel forms must include the `.verify-money-input` class (defined in `resources/css/filament/admin/theme.css`) via `->extraAttributes(['class' => 'verify-money-input'])` to hide browser arrow toggles and ensure consistent cross-browser styling.

## Blade & Views

1. **Never use `@error`, `@click`, `@if` etc. as Alpine/JS listeners inside Blade.** Blade interprets `@error` as its validation directive (`@error … @enderror`), so ` <img @error="…">` inside a Blade file throws `ParseError: unexpected end of file, expecting "elseif" or "else" or "endif"` and takes down every panel page that includes the partial. Always use `x-on:error`, `x-on:click`, etc. for Alpine.
2. **PowerShell edits must preserve newlines in PHP files.** Piping `Get-Content | Where-Object | Set-Content -NoNewline` (or similar) can strip the newline between `<?php` and `return` in locale files, producing `<?phpreturn` and a `ParseError` on every request. Prefer the `Read`/`Edit` tools and verify with `php -l` before deploying.
3. **Clear and actually render after any Blade change.** Run `php artisan view:clear && php artisan optimize:clear` and then render a panel page (`view('filament.pages.partials.…')->render()` or `php vendor/bin/pest tests/Feature/ReceptionPageTest.php`) before reporting the fix — stale `storage/framework/views` hides compile errors until the next cold deploy.

## Code Reuse

1. **Prefer reusable code.** Before writing new logic, check for existing helpers, traits, services, or Filament components that already handle the same use case. Duplicate code is a liability — extract shared logic into reusable pieces instead of copy-pasting.
2. **Extract repeated patterns.** If a block of code appears in two or more places, refactor it into a shared method, class, or component. This applies to Blade views, PHP classes, JS, and Filament resources alike.
3. **Use existing packages and utilities.** Do not reinvent functionality that an existing package or framework feature already provides. Check the project's `composer.json` and `package.json` for available tools before writing custom solutions.
4. **Don't create a parallel concept when an existing one already models it.** Before adding a new status, enum, or flag, check whether an existing one can be extended to cover the new case — two overlapping ways to represent the same state is a redundancy bug waiting to happen, not just duplicated code.
5. **Shared logic should work for any location, not just the one you're testing against.** Since locations are meant to be self-contained tenants, a helper/service/component built while working on one location's flow shouldn't hardcode assumptions (a specific theme, a specific plan name) that break for another.

## Code Style – Comments

1. **Do not write comments in code files.** Never add comments to PHP, JS, TS, Blade, CSS, or any other code files — no `//`, `/* */`, `/** */`, `#`, `<!-- -->`, or `{{-- --}}`, including explanatory, section-header, or commented-out code blocks. Code must be self-documenting through clear names and structure. Documentation (`.md`) files may contain prose where necessary, but code files must not.
2. **Remove existing comments when touching a file.** If you edit a file that contains comments, remove them in the same change unless they are legally required (e.g., license headers).
3. **Do not use comments as a place for long-winded chain-of-thought.** Long thinking texts must be generated as private reasoning. Comments in code must be appropriately concise — which in this project means absent.

## JavaScript & Vite

1. **Never use bare imports in inline `<script>` blocks in Blade views.** Vite only bundles files in its graph (`resources/js/*`). An inline `import Echo from 'laravel-echo'` inside a Blade view is emitted as-is; the browser cannot resolve the package specifier, throws `Failed to resolve module specifier`, and the whole script silently dies.
2. **Use the bundled globals already exposed by `resources/js/*` entries.** `app.js` sets `window.Echo` (Reverb), `window.Pusher`, and `window.axios`. Inline page scripts should consume these (`const echo = window.Echo;`) instead of re-importing or re-initialising Echo.
3. **Wait for `DOMContentLoaded` before using bundled globals.** Vite output loads as deferred module scripts, which run AFTER a plain inline script during HTML parsing. Inline scripts that touch `window.Echo` (or any module-exposed global) must wrap their logic in `document.addEventListener('DOMContentLoaded', ...)`.
4. **Put new JS in `resources/js/` and load it via `@vite`, not inline.** If the feature needs behaviour not covered by the bundled entries, add a module file there and include it through the `@vite` directive in the view.

## Real-Time & Live Updates (Broadcasting)

1. **A change to shared state isn't done until it broadcasts.** If a mutation is something another logged-in user (a different tab, a different staff member, a different location dashboard) should see — check-ins, queue state, membership/subscription status, overrides — updating the current Livewire component's own state is not sufficient. Fire the event on the relevant channel in the same action that persists the change.
2. **Scope channels per location/tenant, never a single global channel.** Use private/presence channels namespaced by location id (or the specific queue/member uuid), so staff logged into one location's panel never receive another location's events — this is the broadcasting equivalent of the location-scoping already required elsewhere in this doc.
3. **Listeners re-fetch/reconcile, they don't blindly apply a delta.** Reverb connections drop and redeliver (tab backgrounded, laptop sleep, flaky network) — a handler that increments a counter or toggles a flag purely from the event payload will drift over time. On receiving an event, re-fetch or re-render the affected record from the server as the source of truth; treat the broadcast as a "something changed, go check" signal, not the data itself.
4. **Handle reconnect explicitly — don't trust in-memory state after a gap.** When Echo reconnects after a drop, assume events were missed and re-sync the visible page/query rather than continuing to trust whatever the client last had in memory.
5. **Broadcast payloads follow the same exposure rules as the rendered page (rule 11 under UI/UX Quality).** Build the payload for the least-privileged listener on that channel — if a field shouldn't be visible on a given screen, it shouldn't be in the event data either, regardless of whether the current UI happens to hide it.
6. **Live-updating Livewire components subscribe to their own events**, via `#[On(echo: ...)]` or `getListeners()`, and update in place — never require a manual page refresh to see another user's action. Show a reasonable loading/empty state while waiting for the first event or initial fetch.
7. **The broadcast is a refresh signal, not a second source of truth.** When two tabs act on the same record close together (two staff both handling the same check-in), the DB transaction and duplicate/lock rules already in this doc are what actually decide the outcome — the event just tells other tabs to re-fetch and show it, so there's nothing to reconcile client-side beyond "pull the current state."
8. **Broadcasting a side effect goes through the queue** (per the Production Readiness rule on queued jobs), so a slow or failed broadcast never blocks or breaks the request that made the actual change.
9. **New features that touch shared state need a test asserting the right event fires on the right channel** — same expectation as the existing rule that UI-exposure changes get a test locking them in.

## UI / UX Quality

1. **Every pixel matters.** Treat spacing, alignment, and visual hierarchy as first-class concerns. If a layout looks off, fix it — don't leave it for later.
2. **Consistency across views.** Admin panel pages and public-facing pages should feel like part of the same product. Reuse the same patterns (e.g., card styling, form layouts, button styles) wherever possible.
3. **No unnecessary code.** Do not add dead code, commented-out blocks, debug logging, or placeholder logic "just in case". Every line you write is a maintenance burden — keep only what the feature actually needs.
4. **No half-measures.** If a UI element or interaction is worth adding, finish it properly — correct spacing, responsive behaviour, RTL support, loading states, and empty states. An incomplete feature is worse than no feature.
5. **Think in components.** Before building a new UI block, check if an existing component or partial already solves the problem. If you find yourself duplicating markup or styles, extract a reusable piece instead.
6. **Respect the user's time.** Interfaces should be fast, clear, and predictable. Avoid adding visual noise, redundant steps, or overly complex interactions that don't serve a clear purpose.
7. **Phone numbers with a separate dial-code input are always displayed without the country code.** The dial code is its own concept (a split input); the local-number input must never show the prefixed number. Use `Helpers::parsePhoneField()` to split stored values (it always strips the prefix, even for codes not in the known list) and `Helpers::combinePhoneField()` to save (it normalizes the stored value).
8. **Phone numbers displayed read-only (not in an edit input) must show the full number with country code.** Use the raw stored value (e.g. `$member->contact`) directly, not `parsePhoneField()[1]`, so staff can see the complete number including the international dial prefix. Only strip the country code when populating a split dial-code + local-number edit input (per rule 7).
9. **Select dropdowns must always have a preselected value — never an empty placeholder.** A blank "--" or empty option forces the user to click before they can act, and in Livewire forms the `null` state can cause subtle bugs. Always default to the most likely choice (e.g. the first option, the user's current location). Use `->default()` on Filament Select fields, or set the first `<option>` as selected in Blade `<select>` elements. **Exceptions — leave empty:** Country selects (too many options, no single "right" default) and date selects that represent a deadline or historical event (not "today") should keep their empty placeholder. No DatePicker should have `->default(now())` — staff must consciously pick every date.
10. **No redundant buttons.** Never add a control whose only function duplicates another control already on the same view — e.g. a "Skip" button next to a modal's X close button. One control per function; if a footer has a single action, render it alone (full width) instead of padding the row with look-alike alternatives.
11. **Removing something from the UI means removing its exposure, not just hiding it.** When data stops being displayed to a visitor or member (staff names, queue positions, internal reasons, PII), strip it from every surface the browser can still read: broadcast/websocket payloads on public channels (e.g. `queue.{uuid}`), JSON/API responses, inline `@json` blobs and JS message maps, rendered HTML/meta tags, and dead CSS/markup left behind. A hidden element still ships the data to anyone who opens devtools. Search views, events, and controllers before calling the cleanup done — and lock it in with a test asserting the data no longer leaves for the public side.

## Modals (Filament)

1. **Open each Filament modal exactly once.** Never combine an `x-init="$nextTick(() => open())"` on a `<x-filament::modal>` with an `open-modal` dispatch from PHP (`$this->dispatch('open-modal', id: ...)`). The double open can leave a semi-transparent white window stuck on top of the modal. Pick ONE mechanism per modal — the `open-modal` dispatch (Livewire) is the preferred pattern (see `AddSubscriptionModal::mount()` / `openForm()`); if a modal must auto-open on mount, do it via the dispatch, not via `x-init`.
2. **When swapping one modal for another, close the first before opening the second.** Dispatch `close-modal` for the current modal before `open-modal` for the next one (same Livewire request, that order). Do not leave two modals open at once.

## Deployment & Networking (Tailscale Funnel)

1. **Never run `tailscale serve --https=...` on the funnel domain.** `tailscale serve` makes a host tailnet-only and removes it from the public internet. The correct command for public access is `tailscale funnel --bg --https=443 http://127.0.0.1:80`. Always run `tailscale serve status` after any Tailscale networking change to confirm the `Funnel on:` line still lists the correct domain.
2. **Restart commands after a Docker rebuild:** `docker compose -f docker-compose.yml -f docker-compose.https.yml --profile https down && docker compose -f docker-compose.yml -f docker-compose.https.yml --profile https up -d && docker compose exec app php artisan optimize:clear`. Always include the HTTPS profile and compose override — using bare `docker compose up -d` drops the TLS config and breaks `:8443`.
3. **DNS for `*.ts.net` returns both IPv4 and IPv6.** Tailscale's public DNS advertises AAAA records (DERP relay IPs) alongside A records. If IPv6 is unreachable from the client's network, Android's Happy Eyeballs algorithm may try IPv6 first, hang, and show "connection closed." If a phone or tablet cannot reach the public funnel URL, have the user clear Chrome's DNS cache (`chrome://net-internals/#dns`), try an incognito window, or switch between WiFi and mobile data. Do not assume the server is broken — verify externally with `curl` to the public IPs or `WebFetch` before restarting the stack.
4. **The server is currently on a laptop but will migrate to a desktop.** Any machine running the server will resolve `torogym.taild62334.ts.net` to its own Tailscale IP (currently `100.119.99.127` on the laptop) via MagicDNS, which means it never hits the public funnel edge. Test public pages from a device that is **not** on the tailnet — a phone with Tailscale uninstalled, on mobile data, is ideal. Do not waste time debugging "the public URL doesn't work" from the machine that hosts the server. When migrating to the desktop, re-run `tailscale funnel --bg --https=443 http://127.0.0.1:80` and `tailscale serve --bg --https=8443 http://127.0.0.1:81` on the new machine and verify `tailscale serve status` shows the correct domain and IPs.
5. **Funnel token URLs are the only way to reach public check-in/signup.** The bare domain `https://torogym.taild62334.ts.net/` without a token path returns 404 by design (no matching nginx server block). Always include the full token URL (e.g. `/checkin/{token}`) when testing or printing QR codes. Old tokens are deleted on rotation — re-print from Reception → QR Codes after any rotation.
6. **Every completed task must be deployed to the live server and verified there before it is considered done.** After local `php artisan test` passes, rebuild and redeploy so the running containers actually serve the new code: if JS/CSS changed `docker compose build app` (Vite runs in the build stage), then the HTTPS-profile restart from rule 2, then `docker compose exec app php artisan optimize:clear`. Verify on the live URL from a non-tailnet device (or via `docker compose exec app php artisan tinker` / `docker compose logs reverb --tail` and a manual toggle) that the DB persisted (`sound_alerts` / theme), the icon/state flipped in the acting tab, **and** the other open tab followed live over Reverb (no refresh). Do not mark a task done on local tests alone — the live Funnel + Reverb + Vite build is the source of truth.
7. **If the public Funnel URL fails TLS on phones but works from another external network, the Funnel registration itself is the suspect — reset and recreate it.** Symptoms of a stale/corrupted registration: iPhone Safari `couldn't establish a secure connection` on both Wi-Fi and cellular while an external fetch returns HTTP 200; public DNS answers differ by resolver (some return relay IPs, some return NXDOMAIN); direct TLS to the advertised relay IPs connects on TCP but never returns a ServerHello; `tailscale debug daemon-logs` stays silent during a failed attempt (proving the drop is upstream of tailscaled, not a node filter/cap deny). Do not touch Docker, nginx, Laravel, dependencies, or the DB for this — it is Tailscale-side. Procedure: first preserve `tailscale funnel status` and `tailscale serve status`; then `tailscale funnel reset` and confirm both show `No serve config`; then recreate with `tailscale funnel --bg --https=443 http://127.0.0.1:80`. Note `funnel reset` wipes the whole serve config including the private `:8443` mapping, so immediately restore it with `tailscale serve --bg --https=8443 http://127.0.0.1:81` and confirm both statuses match the preserved state. Then wait at least 5 minutes (Funnel DNS changes take up to 5 minutes to propagate), verify DNS answers `Status: 0` with relay IPs from Google DoH for both A and AAAA, fetch a public token URL externally for HTTP 200, confirm `:8443/login` still returns 200, and retest the phone on cellular first. If it still fails after that, do not re-register again — escalate to Tailscale Support with the version, both statuses, the DNS inconsistency table, relay probe results, and a `tailscale bugreport` ID.

## Reporting & Verification Honesty

1. **Never present assumed, expected, or simulated output as if it were a real command result.** If you cannot execute something (browser automation, a live click, a query against a system you don't have access to), say so explicitly instead of writing plausible-looking output.
2. **Every claimed “live verification” must be labeled with exactly how it was obtained** (raw terminal paste vs Livewire test call vs description) so it is possible to tell real evidence from simulated evidence at a glance.
3. **If a verification step requires manual UI interaction, state that you are waiting for the user to perform it** and do not fabricate the post-action DB rows or screenshot content in advance.
